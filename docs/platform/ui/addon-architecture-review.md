# Addon Architecture Review: foundation-ui-app

**Project**: IQKV Foundation UI App (Multi-tenant SaaS React Application)  
**Architecture**: Feature-Sliced Design (FSD)  
**Date**: 2026-07-22  
**Purpose**: Architectural analysis for supporting addon functionality

---

## Executive Summary

The foundation-ui-app is a well-architected React application following Feature-Sliced Design (FSD) with strict layer boundaries. The architecture already demonstrates several patterns conducive to addon development:

**Strengths**:

- ✅ Clear separation of concerns via FSD layers
- ✅ Feature isolation with public APIs (`index.ts`)
- ✅ Centralized routing system (TanStack Router)
- ✅ Shared infrastructure (API, UI components, utilities)
- ✅ Configuration-driven features (billing entitlements, rollout modes)
- ✅ Strong TypeScript typings throughout

**Current Limitations**:

- ⚠️ No addon discovery/registration mechanism
- ⚠️ Features are statically imported (no dynamic loading)
- ⚠️ Routes are file-based (no runtime route registration)
- ⚠️ Navigation is hardcoded in AppLayout
- ⚠️ No addon lifecycle hooks
- ⚠️ No addon isolation boundaries

**Recommendation**: The project can be enhanced to support addon functionality with a moderate architectural refactoring focusing on: addon registry, dynamic feature loading, route registration, and addon-aware providers.

## 1. Current Architecture Analysis

### 1.1 Layer Structure (FSD)

```
src/
├── app/                    # Application layer - Bootstrap, providers, config
│   ├── app.tsx            # Root component with provider stack
│   ├── config/            # Runtime config, billing constants, rollout guards
│   └── theme.ts           # Mantine theme configuration
├── processes/             # Business processes spanning features
│   ├── session/           # JWT session management (Zustand)
│   ├── theme/             # Color scheme store
│   └── inactivity-timer/  # Auto sign-out timer
├── pages/                 # File-based routes (TanStack Router)
│   ├── __root.tsx         # Root layout
│   ├── _app.tsx           # Authenticated area guard + layout
│   └── [route files]      # Individual page components
├── widgets/               # Composite UI blocks (dashboard widgets)
├── features/              # Isolated user-facing features
│   ├── sign-in/
│   ├── manage-billing/
│   ├── invite-member/
│   └── [21 features]      # Each with ui/, model/, index.ts
├── entities/              # Business entities (user, tenant, notification)
├── shared/                # Shared infrastructure
│   ├── api/              # HTTP client, API modules, auth interceptor
│   ├── lib/              # Utilities (JWT, validation, dates)
│   ├── ui/               # Reusable UI components
│   └── types/            # Global TypeScript types
```

**Key Observation**: The FSD architecture naturally supports modularity. Features are already isolated and expose public APIs.

### 1.2 Feature Structure Pattern

Each feature follows a consistent structure:

```typescript
features/[feature-name]/
├── ui/                    # React components
│   └── [component].tsx
├── model/                 # Hooks, business logic, types
│   └── use-[feature].ts
└── index.ts              # Public API (REQUIRED by architecture tests)
```

**Example: `features/sign-in/`**

```typescript
// index.ts - Public API
export { SignInForm } from "./ui/sign-in-form";
export { TenantPicker } from "./ui/tenant-picker";
export { useSignIn } from "./model/use-sign-in";
export { useTenantDiscovery } from "./model/use-tenant-discovery";
```

**Pluggability Assessment**:

- ✅ Features are self-contained modules
- ✅ Public API pattern enables controlled exposure
- ✅ No direct cross-feature dependencies (orchestration via `processes/`)
- ⚠️ Static imports only - no lazy loading
- ⚠️ No feature metadata (version, dependencies, permissions)

### 1.3 Routing System

**Current Implementation**: TanStack Router with file-based routing

```typescript
// pages/_app.tsx - Protected route layout
export const Route = createFileRoute("/_app")({
  beforeLoad: async ({ location }) => {
    // Auth guard logic - silent refresh, JWT validation
    // Redirects to /sign-in if unauthenticated
  },
  component: AppLayoutRoute,
});
```

**Route Generation**: `src/routeTree.gen.ts` is auto-generated by Vite plugin during build

**Pluggability Assessment**:

- ✅ Strong typing with route inference
- ✅ Centralized auth guard at `_app` layout level
- ✅ Route context for queryClient injection
- ⚠️ File-based = compile-time only
- ⚠️ No runtime route registration API
- ⚠️ Addon routes would require build-time code generation

**Impact**: Adding addon routes requires either:

1. Runtime route registration (switch from file-based to programmatic)
2. Build-time code generation for addon routes
3. Hybrid approach with reserved addon route prefix (our chosen approach)

### 1.4 State Management

**Session State** (`processes/session/`):

- Zustand store (no middleware)
- Manual persistence to sessionStorage
- Imperative accessors for non-React contexts (Axios interceptors)

```typescript
// processes/session/session.store.ts
export const useSessionStore = create<SessionState>((set) => ({
  accessToken: null,
  refreshToken: loadFromStorage(REFRESH_TOKEN_KEY),
  tenantKey: loadFromStorage(TENANT_KEY_KEY),
  setTokens: (accessToken, refreshToken, tenantKey, isPersonalWorkspace) => {
    saveToStorage(REFRESH_TOKEN_KEY, refreshToken);
    // ...
    set({ accessToken, refreshToken, tenantKey, isPersonalWorkspace });
  },
}));

// Public API exports both hook and imperative accessors
export const getAccessToken = (): string | null => useSessionStore.getState().accessToken;
```

**Server State** (TanStack Query):

- Query keys follow convention: `["entity", tenantKey, ...params]`
- Mutations invalidate queries by key patterns
- Shared `queryClient` instance in `shared/lib/query-client.ts`

**Pluggability Assessment**:

- ✅ Process stores are accessible to all features
- ✅ Query client is injectable via router context
- ✅ Clear separation: client state (Zustand) vs server state (Query)
- ⚠️ No addon-specific state namespace
- ⚠️ No state isolation between addons

### 1.5 API Layer

**Architecture**: Single `httpClient` (Axios) with interceptors

```typescript
// shared/api/http-client.ts
export const httpClient = axios.create({
  baseURL: isDev ? "/api" : getConfig("VITE_API_SERVER_URL"),
  withCredentials: !isDev,
});

// shared/api/auth-interceptor.ts (side-effect import)
httpClient.interceptors.request.use((config) => {
  const token = getAccessToken();
  const tenantKey = getTenantKey();

  if (token && !isPublicEndpoint(config.url)) {
    config.headers.Authorization = `Bearer ${token}`;
    config.headers["X-Tenant-ID"] = tenantKey;
  }
  return config;
});

httpClient.interceptors.response.use(
  (response) => response,
  async (error) => {
    // 401 handling - deduplicated silent refresh
  },
);
```

**API Modules** (all in `shared/api/`):

- `authApi` - sign-in, sign-out, token refresh
- `iamApi` - users, tenants, members, invitations
- `billingApi` - plans, subscriptions, entitlements
- `cmsApi` - CMS pages CRUD
- `oauth2Api` - OAuth provider linking
- Each module is a plain object with methods returning `httpClient` promises

**Pluggability Assessment**:

- ✅ Centralized HTTP client for consistent auth injection
- ✅ API modules are thin wrappers (easy to extend)
- ✅ Interceptor pattern for cross-cutting concerns
- ⚠️ Single global client (no per-addon API configuration)
- ⚠️ No API versioning or namespace support for addons

### 1.6 UI Layout and Navigation

**AppLayout** (`shared/ui/app-layout/`):

- Renders navigation sidebar with hardcoded menu items
- Uses `AppShell` from Mantine
- Header with user menu, notifications, locale switcher, theme toggle

**Current Navigation Structure**:

```typescript
// Typical pattern in AppLayout
const menuItems = [
  { label: t`Dashboard`, path: "/", icon: IconHome },
  { label: t`Team`, path: "/team", icon: IconUsers },
  { label: t`Billing`, path: "/billing", icon: IconCreditCard },
  { label: t`Settings`, path: "/account/settings/general", icon: IconSettings },
];
```

**Pluggability Assessment**:

- ⚠️ Navigation is hardcoded in layout component
- ⚠️ No navigation extension points
- ⚠️ No concept of "addon menu items"
- ⚠️ User menu is fixed
- ⚠️ No support for addon-specific sidebar sections

**Required Changes for Addons**:

1. Dynamic navigation registry
2. Menu item sorting/grouping
3. Permission-based visibility
4. Addon icon/badge support

### 1.7 Configuration System

**Multi-layered Configuration**:

1. **Build-time** (`.env` files):

   ```env
   VITE_API_SERVER_URL=https://api.iqkv.site/api
   VITE_ROLLOUT_MODE=MULTI_TENANT
   VITE_ENABLE_MAGIC_LINK=true
   VITE_PAYMENT_GATEWAY_TYPE=STRIPE
   ```

2. **Runtime Override** (`public/config.js`):

   ```javascript
   window.VITE_API_SERVER_URL = "https://api.example.com/api";
   ```

3. **Feature Flags** (`app/config/`):
   ```typescript
   export const BILLING_FEATURES = {
     PRIORITY_SUPPORT: "priority_support",
     ADVANCED_ANALYTICS: "advanced_analytics",
   } as const;
   ```

**Entitlements System** (`features/manage-billing/`):

- Context provider wrapping authenticated routes
- Hooks: `useHasFeature()`, `useQuota()`, `useFeatureValue()`
- `<FeatureGate>` component for conditional rendering

```typescript
// Usage in components
const hasPrioritySupport = useHasFeature(BILLING_FEATURES.PRIORITY_SUPPORT);

<FeatureGate feature={BILLING_FEATURES.ADVANCED_ANALYTICS} showUpgradePrompt>
  <AdvancedAnalyticsDashboard />
</FeatureGate>;
```

**Pluggability Assessment**:

- ✅ Runtime configuration override mechanism exists
- ✅ Feature flag pattern is established
- ✅ Entitlements system can gate features
- ⚠️ No addon-specific configuration schema
- ⚠️ No addon manifest or metadata
- ⚠️ No dynamic feature flag registration

## 2. Addon System Requirements

### 2.1 Addon Definition

An addon should be a self-contained module that can:

1. **Register routes** - Add new pages to the application
2. **Extend navigation** - Add menu items, sections, or tabs
3. **Provide features** - Expose UI components, hooks, and business logic
4. **Access core APIs** - Use HTTP client, session, query client
5. **Declare dependencies** - Specify required features or versions
6. **Define permissions** - Integrate with entitlements/RBAC
7. **Contribute to layouts** - Inject widgets, sidebar items, user menu actions
8. **Handle lifecycle** - Initialize, activate, deactivate, cleanup

### 2.2 Addon Manifest

```typescript
// Example: addons/project-management/addon.manifest.ts
export const addonManifest = {
  id: "project-management",
  name: "Project Management",
  version: "1.0.0",
  author: "IQKV Team",
  description: "Manage projects with Kanban boards and timeline views",

  // Dependencies
  requires: {
    core: ">=0.5.0",
    features: ["manage-billing"],
  },

  // Permissions/Entitlements
  permissions: {
    features: ["project_management"], // Entitlement feature code
    roles: ["TENANT_OWNER", "ADMIN"], // Required user role
  },
};
```

### 2.3 Addon Structure Proposal

Align addons with existing FSD architecture:

```
addons/
├── [addon-id]/
│   ├── addon.manifest.ts     # Addon metadata
│   ├── index.ts              # Addon entry point
│   ├── features/             # Addon-specific features
│   │   └── [feature-name]/
│   │       ├── ui/
│   │       ├── model/
│   │       └── index.ts
│   ├── pages/                # Addon routes
│   │   └── [route].tsx
│   ├── widgets/              # Addon dashboard widgets
│   ├── api/                  # Addon API modules (optional)
│   ├── types/                # Addon TypeScript types
│   └── locales/              # Addon translations
```

## 4. Proposed Addon Architecture

### 4.1 Addon Registry (Core Infrastructure)

**Location**: `src/app/addons/addon-registry.ts`

```typescript
export interface AddonContext {
  httpClient: AxiosInstance;
  queryClient: QueryClient;
  session: {
    useSession: () => SessionState;
    getAccessToken: () => string | null;
    getTenantKey: () => string | null;
  };
  i18n: I18n;
  extensions: {
    navigation: NavigationExtensionPoint;
    widgets: WidgetExtensionPoint;
  };
}

export interface AddonRoute {
  path: string;
  component: LazyExoticComponent<ComponentType<any>>;
  auth?: boolean;
  roles?: string[];
}

export interface Addon {
  manifest: AddonManifest;
  routes?: AddonRoute[];
  initialize?: (context: AddonContext) => void | Promise<void>;
  cleanup?: () => void;
}

class AddonRegistry {
  private addons = new Map<string, Addon>();

  register(addon: Addon): void {
    if (this.addons.has(addon.manifest.id)) {
      throw new Error(`Addon ${addon.manifest.id} already registered`);
    }

    // Validate dependencies
    this.validateDependencies(addon);

    this.addons.set(addon.manifest.id, addon);
  }

  getAddon(id: string): Addon | undefined {
    return this.addons.get(id);
  }

  getAllAddons(): Addon[] {
    return Array.from(this.addons.values());
  }
}

export const addonRegistry = new AddonRegistry();
```

### 4.2 Extension Points

Extension points allow addons to contribute to UI without modifying core code.

```typescript
// src/app/addons/extension-points/navigation.ts
import { type ComponentType } from "react";

export interface NavItemExtension {
  id: string;
  label: string;
  to: string;
  icon: ComponentType<{ size?: number }>;
  order?: number;
  section?: "workspace" | "account";
  roles?: string[];
  feature?: string;
}

export interface NavigationExtensionPoint {
  registerNavItem(item: NavItemExtension): void;
  getNavItems(section: "workspace" | "account"): NavItemExtension[];
}

class NavigationExtensionPointImpl implements NavigationExtensionPoint {
  private items: NavItemExtension[] = [];

  registerNavItem(item: NavItemExtension): void {
    this.items.push(item);
  }

  getNavItems(section: "workspace" | "account"): NavItemExtension[] {
    return this.items
      .filter((item) => !item.section || item.section === section)
      .sort((a, b) => (a.order || 100) - (b.order || 100));
  }
}

export const navigationExtension = new NavigationExtensionPointImpl();
```

```typescript
// src/app/addons/extension-points/widgets.ts
import { type ComponentType } from "react";

export interface WidgetExtension {
  id: string;
  component: ComponentType<any>;
  location: "dashboard";
  order?: number;
}

export interface WidgetExtensionPoint {
  registerWidget(widget: WidgetExtension): void;
  getWidgets(location: "dashboard"): WidgetExtension[];
}

class WidgetExtensionPointImpl implements WidgetExtensionPoint {
  private widgets: WidgetExtension[] = [];

  registerWidget(widget: WidgetExtension): void {
    this.widgets.push(widget);
  }

  getWidgets(location: "dashboard"): WidgetExtension[] {
    return this.widgets
      .filter((w) => w.location === location)
      .sort((a, b) => (a.order || 100) - (b.order || 100));
  }
}

export const widgetExtension = new WidgetExtensionPointImpl();
```

### 4.3 Hybrid Routing Setup

- **Core routes**: Keep file-based (existing `src/pages/`)
- **Addon pages**: Add catch-all route under `/addons/` for dynamic rendering:

```typescript
// src/pages/_app/addons.tsx (new file)
import { createFileRoute, Outlet, useLocation } from "@tanstack/react-router";
import { addonRegistry } from "@/app/addons/addon-registry";
import { AuthGuard } from "@/shared/ui";
import { LoadingOverlay } from "@/shared/ui";
import { Suspense } from "react";

export const Route = createFileRoute("/_app/addons")({
  component: () => <Outlet />,
});

// Catch-all child route for addon pages
export const AddonCatchAllRoute = Route.createRoute({
  path: "/*",
  component: AddonRouteRenderer,
});

function AddonRouteRenderer() {
  const location = useLocation();
  const addons = addonRegistry.getAllAddons();

  // Match current path to addon routes
  const matchedRoute = addons
    .flatMap(p => p.routes || [])
    .find(route => route.path === location.pathname);

  if (!matchedRoute) {
    return <div>404 - Addon page not found</div>;
  }

  const Component = matchedRoute.component;

  // Use existing AuthGuard and FeatureGate for access control
  return (
    <AuthGuard>
      <Suspense fallback={<LoadingOverlay visible />}>
        <Component />
      </Suspense>
    </AuthGuard>
  );
}
```

## 5. Performance Considerations

### 5.1 Bundle Size

- **Concern**: Including all addons in the main bundle could increase bundle size
- **Mitigation**: Use **dynamic imports** for addons - only load addons that are enabled via configuration
- **Tooling**: Use Vite's bundle analyzer to track addon bundle sizes

### 5.2 Initial Load Time

- **Concern**: Loading addons on app initialization could delay first render
- **Mitigation**:
  - Load addons **after** the core app is rendered and interactive
  - Use `Suspense` and `LoadingOverlay` for addon components
  - Prioritize loading critical addons first, lazy-load non-critical addons later

### 5.3 Route Matching

- **Concern**: Catch-all route matching could be slow with many addons
- **Mitigation**:
  - Keep the route matching logic simple (current linear search is fast for reasonable addon counts)
  - For large numbers of addons, pre-process routes into a `Map` for O(1) lookups

### 5.4 Extension Point Registrations

- **Concern**: Too many extension point registrations could cause delays
- **Mitigation**:
  - Keep registration logic lightweight (just pushing to an array)
  - Only register items when the addon is initialized (not on every render)

## 6. Example Addon Implementation

```typescript
// src/addons/project-management/index.ts
import type { Addon } from "@/app/addons/types";
import { ProjectStatsWidget } from "./widgets/project-stats";

const addon: Addon = {
  manifest: {
    id: "project-management",
    name: "Project Management",
    version: "1.0.0",
    description: "Project management features",
  },
  routes: [
    {
      path: "/_app/addons/projects",
      component: () => import("./pages/projects").then((m) => m.ProjectsPage),
      auth: true,
    },
  ],
  initialize: ({ extensions }) => {
    // Register nav item
    extensions.navigation.registerNavItem({
      id: "pm-projects",
      label: "Projects",
      to: "/_app/addons/projects",
      icon: IconChecklist,
      section: "workspace",
      order: 20,
    });

    // Register widget
    extensions.widgets.registerWidget({
      id: "pm-stats",
      component: ProjectStatsWidget,
      location: "dashboard",
      order: 50,
    });
  },
};

export default addon;
```

## 7. Conclusion

This design allows us to:

- Enable/disable features via configuration
- Keep core app clean
- Maintain FSD architecture
- Leverage existing entitlements system
- Provide extension points for addons to contribute UI
- Provide a clear path for future feature modules
- Maintain good performance with dynamic imports and lazy loading
