# Plugin Architecture Review: foundation-ui-app

**Project**: IQKV Foundation UI App (Multi-tenant SaaS React Application)  
**Architecture**: Feature-Sliced Design (FSD)  
**Date**: 2026-07-21  
**Purpose**: Architectural analysis for supporting pluggable functionality

---

## Executive Summary

The foundation-ui-app is a well-architected React application following Feature-Sliced Design (FSD) with strict layer boundaries. The architecture already demonstrates several patterns conducive to plugin development:

**Strengths**:

- ✅ Clear separation of concerns via FSD layers
- ✅ Feature isolation with public APIs (`index.ts`)
- ✅ Centralized routing system (TanStack Router)
- ✅ Shared infrastructure (API, UI components, utilities)
- ✅ Configuration-driven features (billing entitlements, rollout modes)
- ✅ Strong TypeScript typings throughout

**Current Limitations**:

- ⚠️ No plugin discovery/registration mechanism
- ⚠️ Features are statically imported (no dynamic loading)
- ⚠️ Routes are file-based (no runtime route registration)
- ⚠️ Navigation is hardcoded in AppLayout
- ⚠️ No plugin lifecycle hooks
- ⚠️ No plugin isolation boundaries

**Recommendation**: The project can be enhanced to support pluggable functionality with a moderate architectural refactoring focusing on: plugin registry, dynamic feature loading, route registration, and plugin-aware providers.

## 1. Current Architecture Analysis

### 1.1 Layer Structure (FSD)

```
src/
├── app/                    # Application layer - Bootstrap, providers, config
│   ├── app.tsx            # Root component with provider stack
│   ├── config/            # Runtime config, billing constants, rollout guards
│   └── theme.ts           # Mantine theme configuration
├── processes/             # Business processes spanning features
│   ├── session/           # JWT session management (Zustand)
│   ├── theme/             # Color scheme store
│   └── inactivity-timer/  # Auto sign-out timer
├── pages/                 # File-based routes (TanStack Router)
│   ├── __root.tsx         # Root layout
│   ├── _app.tsx           # Authenticated area guard + layout
│   └── [route files]      # Individual page components
├── widgets/               # Composite UI blocks (dashboard widgets)
├── features/              # Isolated user-facing features
│   ├── sign-in/
│   ├── manage-billing/
│   ├── invite-member/
│   └── [21 features]      # Each with ui/, model/, index.ts
├── entities/              # Business entities (user, tenant, notification)
├── shared/                # Shared infrastructure
│   ├── api/              # HTTP client, API modules, auth interceptor
│   ├── lib/              # Utilities (JWT, validation, dates)
│   ├── ui/               # Reusable UI components
│   └── types/            # Global TypeScript types
```

**Key Observation**: The FSD architecture naturally supports modularity. Features are already isolated and expose public APIs.

### 1.2 Feature Structure Pattern

Each feature follows a consistent structure:

```typescript
features/[feature-name]/
├── ui/                    # React components
│   └── [component].tsx
├── model/                 # Hooks, business logic, types
│   └── use-[feature].ts
└── index.ts              # Public API (REQUIRED by architecture tests)
```

**Example: `features/sign-in/`**

```typescript
// index.ts - Public API
export { SignInForm } from "./ui/sign-in-form";
export { TenantPicker } from "./ui/tenant-picker";
export { useSignIn } from "./model/use-sign-in";
export { useTenantDiscovery } from "./model/use-tenant-discovery";
```

**Pluggability Assessment**:

- ✅ Features are self-contained modules
- ✅ Public API pattern enables controlled exposure
- ✅ No direct cross-feature dependencies (orchestration via `processes/`)
- ⚠️ Static imports only - no lazy loading
- ⚠️ No feature metadata (version, dependencies, permissions)

### 1.3 Routing System

**Current Implementation**: TanStack Router with file-based routing

```typescript
// pages/_app.tsx - Protected route layout
export const Route = createFileRoute("/_app")({
  beforeLoad: async ({ location }) => {
    // Auth guard logic - silent refresh, JWT validation
    // Redirects to /sign-in if unauthenticated
  },
  component: AppLayoutRoute,
});
```

**Route Generation**: `src/routeTree.gen.ts` is auto-generated by Vite plugin during build

**Pluggability Assessment**:

- ✅ Strong typing with route inference
- ✅ Centralized auth guard at `_app` layout level
- ✅ Route context for queryClient injection
- ⚠️ File-based = compile-time only
- ⚠️ No runtime route registration API
- ⚠️ Plugin routes would require build-time code generation

**Impact**: Adding plugin routes requires either:

1. Runtime route registration (switch from file-based to programmatic)
2. Build-time code generation for plugin routes
3. Hybrid approach with reserved plugin route prefix

### 1.4 State Management

**Session State** (`processes/session/`):

- Zustand store (no middleware)
- Manual persistence to sessionStorage
- Imperative accessors for non-React contexts (Axios interceptors)

```typescript
// processes/session/session.store.ts
export const useSessionStore = create<SessionState>((set) => ({
  accessToken: null,
  refreshToken: loadFromStorage(REFRESH_TOKEN_KEY),
  tenantKey: loadFromStorage(TENANT_KEY_KEY),
  setTokens: (accessToken, refreshToken, tenantKey, isPersonalWorkspace) => {
    saveToStorage(REFRESH_TOKEN_KEY, refreshToken);
    // ...
    set({ accessToken, refreshToken, tenantKey, isPersonalWorkspace });
  },
}));

// Public API exports both hook and imperative accessors
export const getAccessToken = (): string | null => useSessionStore.getState().accessToken;
```

**Server State** (TanStack Query):

- Query keys follow convention: `["entity", tenantKey, ...params]`
- Mutations invalidate queries by key patterns
- Shared `queryClient` instance in `shared/lib/query-client.ts`

**Pluggability Assessment**:

- ✅ Process stores are accessible to all features
- ✅ Query client is injectable via router context
- ✅ Clear separation: client state (Zustand) vs server state (Query)
- ⚠️ No plugin-specific state namespace
- ⚠️ No state isolation between plugins

### 1.5 API Layer

**Architecture**: Single `httpClient` (Axios) with interceptors

```typescript
// shared/api/http-client.ts
export const httpClient = axios.create({
  baseURL: isDev ? "/api" : getConfig("VITE_API_SERVER_URL"),
  withCredentials: !isDev,
});

// shared/api/auth-interceptor.ts (side-effect import)
httpClient.interceptors.request.use((config) => {
  const token = getAccessToken();
  const tenantKey = getTenantKey();

  if (token && !isPublicEndpoint(config.url)) {
    config.headers.Authorization = `Bearer ${token}`;
    config.headers["X-Tenant-ID"] = tenantKey;
  }
  return config;
});

httpClient.interceptors.response.use(
  (response) => response,
  async (error) => {
    // 401 handling - deduplicated silent refresh
  },
);
```

**API Modules** (all in `shared/api/`):

- `authApi` - sign-in, sign-out, token refresh
- `iamApi` - users, tenants, members, invitations
- `billingApi` - plans, subscriptions, entitlements
- `cmsApi` - CMS pages CRUD
- `oauth2Api` - OAuth provider linking
- Each module is a plain object with methods returning `httpClient` promises

**Pluggability Assessment**:

- ✅ Centralized HTTP client for consistent auth injection
- ✅ API modules are thin wrappers (easy to extend)
- ✅ Interceptor pattern for cross-cutting concerns
- ⚠️ Single global client (no per-plugin API configuration)
- ⚠️ No API versioning or namespace support for plugins

### 1.6 UI Layout and Navigation

**AppLayout** (`shared/ui/app-layout/`):

- Renders navigation sidebar with hardcoded menu items
- Uses `AppShell` from Mantine
- Header with user menu, notifications, locale switcher, theme toggle

**Current Navigation Structure**:

```typescript
// Typical pattern in AppLayout
const menuItems = [
  { label: t`Dashboard`, path: "/", icon: IconHome },
  { label: t`Team`, path: "/team", icon: IconUsers },
  { label: t`Billing`, path: "/billing", icon: IconCreditCard },
  { label: t`Settings`, path: "/account/settings/general", icon: IconSettings },
];
```

**Pluggability Assessment**:

- ⚠️ Navigation is hardcoded in layout component
- ⚠️ No navigation extension points
- ⚠️ No concept of "plugin menu items"
- ⚠️ User menu is fixed
- ⚠️ No support for plugin-specific sidebar sections

**Required Changes for Plugins**:

1. Dynamic navigation registry
2. Menu item sorting/grouping
3. Permission-based visibility
4. Plugin icon/badge support

### 1.7 Configuration System

**Multi-layered Configuration**:

1. **Build-time** (`.env` files):

   ```env
   VITE_API_SERVER_URL=https://api.iqkv.site/api
   VITE_ROLLOUT_MODE=MULTI_TENANT
   VITE_ENABLE_MAGIC_LINK=true
   VITE_PAYMENT_GATEWAY_TYPE=STRIPE
   ```

2. **Runtime Override** (`public/config.js`):

   ```javascript
   window.VITE_API_SERVER_URL = "https://api.example.com/api";
   ```

3. **Feature Flags** (`app/config/`):
   ```typescript
   export const BILLING_FEATURES = {
     PRIORITY_SUPPORT: "priority_support",
     ADVANCED_ANALYTICS: "advanced_analytics",
   } as const;
   ```

**Entitlements System** (`features/manage-billing/`):

- Context provider wrapping authenticated routes
- Hooks: `useHasFeature()`, `useQuota()`, `useFeatureValue()`
- `<FeatureGate>` component for conditional rendering

```typescript
// Usage in components
const hasPrioritySupport = useHasFeature(BILLING_FEATURES.PRIORITY_SUPPORT);

<FeatureGate feature={BILLING_FEATURES.ADVANCED_ANALYTICS} showUpgradePrompt>
  <AdvancedAnalyticsDashboard />
</FeatureGate>
```

**Pluggability Assessment**:

- ✅ Runtime configuration override mechanism exists
- ✅ Feature flag pattern is established
- ✅ Entitlements system can gate features
- ⚠️ No plugin-specific configuration schema
- ⚠️ No plugin manifest or metadata
- ⚠️ No dynamic feature flag registration

## 2. Plugin System Requirements

### 2.1 Plugin Definition

A plugin should be a self-contained module that can:

1. **Register routes** - Add new pages to the application
2. **Extend navigation** - Add menu items, sections, or tabs
3. **Provide features** - Expose UI components, hooks, and business logic
4. **Access core APIs** - Use HTTP client, session, query client
5. **Declare dependencies** - Specify required features or versions
6. **Define permissions** - Integrate with entitlements/RBAC
7. **Contribute to layouts** - Inject widgets, sidebar items, user menu actions
8. **Handle lifecycle** - Initialize, activate, deactivate, cleanup

### 2.2 Plugin Manifest

```typescript
// Example: plugins/project-management/plugin.manifest.ts
export const pluginManifest = {
  id: "project-management",
  name: "Project Management",
  version: "1.0.0",
  author: "IQKV Team",
  description: "Manage projects with Kanban boards and timeline views",

  // Dependencies
  requires: {
    core: ">=0.5.0",
    features: ["manage-billing"],
  },

  // Permissions/Entitlements
  permissions: {
    features: ["project_management"], // Entitlement feature code
    roles: ["TENANT_OWNER", "ADMIN"], // Required user role
  },

  // Extension points
  routes: [
    { path: "/projects", component: "ProjectListPage", auth: true },
    { path: "/projects/:id", component: "ProjectDetailPage", auth: true },
  ],

  navigation: {
    primary: [{ label: "Projects", path: "/projects", icon: "IconChecklist", order: 20 }],
  },

  widgets: {
    dashboard: ["ProjectStatsWidget"],
  },
};
```

### 2.3 Plugin Structure Proposal

Align plugins with existing FSD architecture:

```

├── [plugin-id]/
│   ├── plugin.manifest.ts     # Plugin metadata
│   ├── index.ts               # Plugin entry point
│   ├── features/              # Plugin-specific features
│   │   └── [feature-name]/
│   │       ├── ui/
│   │       ├── model/

│   ├── pages/                 # Plugin routes
│   │   └── [route].tsx
│   ├── widgets/               # Plugin dashboard widgets
│   ├── api/                   # Plugin API modules (optional)
│   ├── types/                 # Plugin TypeScript types
│   └── locales/               # Plugin translations
```

## 3. Proposed Plugin Architecture

### 3.1 Plugin Registry (Core Infrastructure)

**Location**: `src/app/plugins/plugin-registry.ts`

```typescript
export interface PluginContext {
  httpClient: AxiosInstance;
  queryClient: QueryClient;
  session: {
    useSession: () => SessionState;
    getAccessToken: () => string | null;
    getTenantKey: () => string | null;
  };
  router: Router;
  i18n: I18n;
}

export interface PluginRoute {
  path: string;
  component: LazyExoticComponent<ComponentType<any>>;
  auth?: boolean;
  roles?: string[];
}

export interface PluginNavigationItem {
  label: string;
  path: string;
  icon?: ComponentType<{ size?: number }>;
  order?: number;
  roles?: string[];
  feature?: string; // Entitlement feature code
}

export interface Plugin {
  manifest: PluginManifest;
  routes: PluginRoute[];
  navigation: {
    primary?: PluginNavigationItem[];
    userMenu?: PluginNavigationItem[];
  };
  widgets?: Record<string, ComponentType<any>>;
  initialize?: (context: PluginContext) => void | Promise<void>;
  cleanup?: () => void;
}

class PluginRegistry {
  private plugins = new Map<string, Plugin>();

  register(plugin: Plugin): void {
    if (this.plugins.has(plugin.manifest.id)) {
      throw new Error(`Plugin ${plugin.manifest.id} already registered`);
    }

    // Validate dependencies
    this.validateDependencies(plugin);

    this.plugins.set(plugin.manifest.id, plugin);
  }

  getPlugin(id: string): Plugin | undefined {
    return this.plugins.get(id);
  }

  getAllPlugins(): Plugin[] {
    return Array.from(this.plugins.values());
  }

  getRoutes(): PluginRoute[] {
    return this.getAllPlugins().flatMap((p) => p.routes);
  }

  getNavigation(): PluginNavigationItem[] {
    return this.getAllPlugins()
      .flatMap((p) => p.navigation.primary || [])
      .sort((a, b) => (a.order || 100) - (b.order || 100));
  }
}

export const pluginRegistry = new PluginRegistry();
```

### 3.2 Dynamic Route Registration

**Challenge**: TanStack Router uses file-based routes (compile-time)

**Solution**: Hybrid approach with programmatic route children

```typescript
// pages/_app.plugins.tsx - New route for plugin pages
import { createFileRoute, Outlet } from "@tanstack/react-router";
import { PluginRouteRenderer } from "@/app/plugins/plugin-route-renderer";

export const Route = createFileRoute("/_app/plugins")({
  component: () => <Outlet />,
});

// Register a catch-all child route programmatically
export const pluginsRoute = createRoute({
  getParentRoute: () => appRoute,
  path: "plugins/*",
  component: PluginRouteRenderer,
});
```

**PluginRouteRenderer**:

```typescript
// app/plugins/plugin-route-renderer.tsx
export function PluginRouteRenderer() {
  const location = useLocation();
  const plugins = pluginRegistry.getAllPlugins();

  // Match current path to plugin routes
  const matchedRoute = plugins
    .flatMap(p => p.routes)
    .find(route => matchesPath(route.path, location.pathname));

  if (!matchedRoute) {
    return <NotFoundPage />;
  }

  const Component = matchedRoute.component;

  // Check auth and permissions
  if (matchedRoute.auth) {
    return (
      <AuthGuard>
        <RoleGuard roles={matchedRoute.roles}>
          <Suspense fallback={<LoadingOverlay visible />}>
            <Component />
          </Suspense>
        </RoleGuard>
      </AuthGuard>
    );
  }

  return (
    <Suspense fallback={<LoadingOverlay visible />}>
      <Component />
    </Suspense>
  );
}
```

**Alternative**: Use TanStack Router's experimental `routeConfig` API for full programmatic routing.
